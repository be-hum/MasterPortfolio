# OLE / HWP text extraction: measured results (M0 Task 0.1)

Date: 2026-11-24. Spike code: `spikes/ole/` (throwaway; samples, outputs, venv and node_modules are gitignored).
Reproduce: `cd spikes/ole && npm i && node extract-hwp-min.mjs && node extract-hwp-hwpjs.mjs && node extract-hwpx.mjs && node extract-doc.mjs && node extract-ppt.mjs && ./extract-pyhwp.sh && ./extract-pyhwp-xml.sh && node build-expected.mjs && node score.mjs`
(python helpers always run as `python3 -I`; Java oracle: `java/PoiText.java` against Apache POI 5.4.1 jars downloaded into `out/jars`).

## Decisions (one line each)

| Format | Decision |
|---|---|
| HWP 5.0 | **Node: own parser (`cfb` + `zlib.inflateRawSync` + `crypto` AES-128-ECB for distribution docs).** pyhwp not needed. |
| HWPX | **Node: own parser (`jszip` + XML walk of `Contents/section*.xml`).** Encrypted/distribution HWPX unsupported (detect and report). |
| DOC | **Node: `word-extractor` (MIT)**; own `cfb` piece-table parser (~60 lines) scores the same and is the fallback. Word 6/95 unsupported (report). |
| PPT | **Node: own parser (`cfb` + record walk with the persist-directory "live" filter).** No npm library was evaluated beyond the brief; the naive walk is NOT sufficient (0.37). |

No Python bundle is required for any of the four formats. Score bar was mean >= 0.9.

## Method and honesty notes

* No user samples were provided and no office viewer (Hancom/MS Office/LibreOffice) is installed. All samples are public files; "expected text" therefore comes from independent sources, not a viewer:
  * `gov1..gov6` (HWP + HWPX): six Korean government press releases from korea.kr (2026-11-20..24). Each is posted as .hwp + .hwpx + .pdf of the **same** document; expected = pypdf text of the PDF (independent of every candidate), page-number lines dropped. For `gov2` (distribution/배포용 doc, table-heavy statistics) PDF text order is unusable (character-bag overlap with the HWP text only 0.55), so expected = pyhwp-xml text; `hwp-cfb-min` independently agrees with it at similarity 1.0 over the first 2,000 chars. gov2 is therefore a two-candidate cross-check, not independent of pyhwp.
  * `pyhwp-*`, `hwpjs-*` (HWP fixtures from the pyhwp and hwp.js test suites): no sibling document. Expected = pyhwp `hwp5proc xml` text, cross-checked against `hwp-cfb-min` and `hwp-hwpjs-deep` (they agree to within ordering of nested table cells). **Circular for pyhwp-xml (it scores 1.0 by construction); read those rows as agreement between candidates.** `pyhwp-matrix` (equations only, no text) and `pyhwp-password-12345` (encrypted) have no expected text and are not scored.
  * DOC/PPT (`poi-*` from Apache POI test-data, `tika-*` from Apache Tika test-documents): expected = Apache POI 5.4.1 (HWPF `WordExtractor.getParagraphText`, HSLF text shapes), a mature independent Java implementation. POI is not ground truth: it leaves Word field instructions inline (I strip `0x13..0x14` before comparing) and skips PPT table-cell text (so a candidate that reads tables is mildly penalised, e.g. `tika-testPPT_various`).
* Score = 1 - Levenshtein/max(len) on the first 2,000 characters, after NFC and removing all whitespace/control chars (`score.mjs`, `score-lib.mjs`). Whitespace/newline differences are ignored by design.
* **Sample counts: HWP 15 (13 scored; 6 gov + 9 fixtures incl. 1 encrypted, 1 equation-only), HWPX 6 (all government-generated; 5 scored independently + 1 encrypted), DOC 8 (7 scored + 1 Word 6/95), PPT 8.** Samples are small in number; scores are indicative, not statistical.
* **Not tested: Korean-language DOC/PPT.** I could not find public Korean .doc/.ppt files (korea.kr now publishes hwp/hwpx/pdf/odt only). DOC/PPT samples are English plus CJK PPT (`54880_chinese`: Japanese kana/Han, supplementary-plane chars; `bug55902`: mixed CJK fonts). Korean text in DOC is normally stored as UTF-16 pieces, which the parser handles; "compressed" pieces are Windows-1252 only. Treat Korean DOC/PPT as a residual risk to re-verify in M2 with a real user file.
* gov4 is an 89 MB .hwp (embedded images): cfb-min parses it in ~270 ms; hwp.js 1.8 s.

### Decisive facts for the M2 implementer (HWP 5.0)

* Container is OLE2/CFB (magic `D0 CF 11 E0`). Streams: `FileHeader` (256 bytes), `DocInfo`, `BodyText/Section0..N`, `ViewText/Section0..N` (distribution docs only), `PrvText` (UTF-16 preview of roughly the first page; handy fallback/sanity text), `BinData/*`, `Scripts/*`, `\x05HwpSummaryInformation`. Sort sections **numerically** (Section10 after Section2).
* `FileHeader`: bytes 0-16 = `"HWP Document File"`; uint32 LE at offset 32 = version (bytes high to low = major.minor.build.revision, e.g. 5.1.1.0); uint32 LE at **offset 36 = flags**: bit0 **compressed** (section streams are raw deflate: `zlib.inflateRawSync`, NOT `inflateSync`, no zlib header), bit1 **password-encrypted**, bit2 **distribution (배포용)**, bit3 script, bit4 DRM, bit8 certificate-encrypted. Check flags before reading; if bit1 (or bit4/bit8) is set, fail with a user-facing "encrypted document" message. Fixture flags seen: gov docs `0x1`; gov2 `0x5` (compressed + distribution).
* Record stream (after decompression): repeated `uint32 LE header`: tag = bits 0-9, level = bits 10-19, size = bits 20-31; if size == 0xFFF the next uint32 is the real size. `HWPTAG_BEGIN = 0x10`. Needed tags: `PARA_HEADER = 0x10+50 = 66`, **`PARA_TEXT = 0x10+51 = 67`**, `CTRL_HEADER = 71`, `LIST_HEADER = 72`, `TABLE = 77`, `DISTRIBUTE_DOC_DATA = 0x10+12 = 28`. Collecting every tag-67 record in stream order already yields body, table cells, footnotes/endnotes, headers/footers and text boxes (they are child records of controls, flattened in order). An empty paragraph has no tag-67 record.
* PARA_TEXT payload is UTF-16LE. Code units >= 32 are text (surrogate pairs OK via `String.fromCharCode` concatenation). Units < 32 are control codes: **char-type** (0, 10, 13, 24-31) occupy 1 unit (10 = line break, 13 = paragraph end, 30/31 = non-breaking/fixed space); **inline** (4-9, 19, 20; 9 = tab) and **extended** (1-3, 11, 12, 14-18, 21-23; table/shape/field/header/footnote anchors) occupy **8 units = 16 bytes** (code + 14 bytes payload + code). Failing to skip those 16 bytes injects garbage characters.
* **Distribution (배포용) docs** (flag bit2; common for government downloads, e.g. gov2): body text is in `ViewText/SectionN`, not `BodyText`. Layout: `[4-byte record header, tag 28][256-byte payload][AES-128-ECB ciphertext]`. Payload decode: `seed = uint32LE(payload[0..3])`; MSVC LCG `seed = seed*214013 + 2531011 (mod 2^32)`, `rand = (seed>>>16) & 0x7fff`; for i in 0..255: if n == 0 { key = rand() & 0xff; n = (rand() & 0xf) + 1 }; if i >= 4 { payload[i] ^= key }; n--. AES key = `payload[off .. off+16]` with `off = 4 + (seed & 0xf)` (the seed is the original first uint32). Then AES-128-ECB (no padding) decrypt the ciphertext tail, then (if flag bit0) `inflateRawSync`, then parse records as usual. No password is needed. Implemented in `spikes/ole/lib.mjs` (`decryptDistribution`); verified identical to pyhwp output on gov2 (copy-restriction flags are not enforced by this; whether to honour them is a product/legal decision for the user's own files).
* Version range seen: 5.0.1.7 to 5.1.1.0; all parsed identically.
* Not done: HWP 3.0 (old non-OLE format) and HWPML (XML) are different formats; detect by magic and report unsupported.

## HWPX

| Candidate | Mean | License | Weight |
|---|---|---|---|
| `hwpx-jszip` (own: unzip, regex over `<hp:p>`/`<hp:t>`) | 0.832 over n=6 = **0.999 over the 5 readable**; gov2 fails by design (encrypted) | jszip: MIT or GPL-3.0 (choose MIT) | 860 KB (+ pako etc.) |

* Package is a ZIP: `mimetype`, `Contents/header.xml`, `Contents/section0.xml..N`, `Contents/content.hpf` (manifest/spine order), `Preview/PrvText.txt`, `BinData/*`, `META-INF/manifest.xml`. Text is in `<hp:t>` inside `<hp:p>` (namespace `http://www.hancom.co.kr/hwpml/2011/paragraph`); `<hp:tab/>` and `<hp:lineBreak/>` are inline siblings; table cells, text boxes and footnotes contain nested `<hp:p>` so a flat regex over `<hp:t>` still reaches them. M2 should use a real XML parser (saxes/fast-xml-parser) instead of my regex, and order sections by number (or by `content.hpf` spine).
* **Encrypted/distribution HWPX**: `META-INF/manifest.xml` contains `odf:encryption-data` for each part (AES-256-CBC, PBKDF2 `key-derivation`, 1024 iterations, SHA-256 start key), section XML is ciphertext (first byte 0xC1, not `<`), `Preview/PrvText.txt` is also ciphertext. gov2 is such a file: extraction returns nothing. Detect it and report; the same document is readable via its .hwp sibling (distribution-doc AES above). I did not attempt to derive the HWPX key.

* Failure: `tika-testWORD6.doc` (Word 6/95, `wIdent = 0xA5DC` instead of 0xA5EC): both reject ("This does not seem to be a Word document" / "bad wIdent"). POI also throws `OldWordFileFormatException`. Unsupported; report it.
* word-extractor scored 0.957 on `testWORD_features` and 0.994 on `HeaderFooterUnicode` where cfb-min scored 1.0 (small differences in field/hyperlink and header handling). Both are fine; word-extractor additionally exposes footnotes, headers and text boxes separately.
* Facts for a hand parser: stream `WordDocument` (FIB: `wIdent` uint16 @0 = 0xA5EC; flags uint16 @0x0A: bit9 = use `1Table` else `0Table`, bit8 = encrypted, bit6/`fComplex`); `ccpText` int32 @76 (also ccpFtn @80, ccpHdd @84; the CP space is main, footnotes, headers, ... concatenated); `fcClx`/`lcbClx` uint32 @0x1A2/0x1A6 into the Table stream. CLX = zero or more `0x01` Prc (size at +1, int16) then `0x02` Pcdt: uint32 lcb, `PlcPcd` = (n+1) CPs (uint32) + n PCDs of 8 bytes (uint16 flags, **uint32 fc**, uint16 prm). If `fc & 0x40000000` the piece is 8-bit (Windows-1252), byte offset `(fc & 0x3FFFFFFF) / 2`; else UTF-16LE at byte offset `fc`. Text chars: 0x0D = paragraph/cell end, 0x07 = table cell/row mark, 0x0B = soft line break, 0x13/0x14/0x15 = field begin/separator/end (keep only the 0x14..0x15 result part, otherwise `HYPERLINK "..."` instructions leak), 0x01/0x08 = picture/drawing anchors (drop). Encrypted DOC: report.

## PPT (PowerPoint 97-2003)

| Candidate | Mean (n=8) | License | Weight |
|---|---|---|---|
| `ppt-cfb-naive` (every TextCharsAtom 0x0FA0 / TextBytesAtom 0x0FA8 in `PowerPoint Document`) | 0.365 | cfb | 0.4 MB |
| `ppt-cfb-slides` (only inside Slide 0x03EE containers and SlideListWithText inst 0) | 0.902 | cfb | same |
| **`ppt-cfb-live`** (additionally walks only records at offsets in the current persist directory) | **0.974** | cfb | same |

* The brief's naive approach is wrong in practice: it also returns master-slide boilerplate ("Click to edit Master title style", bullet `*`), notes text, and **stale duplicates** left by incremental saves (e.g. `basic_test_ppt_file` returns the text twice-plus, 0.235). The working recipe: read `Current User` stream (`offsetToCurrentEdit` uint32 @16), follow `UserEditAtom` (0x0FF5; `offsetLastEdit` = uint32 at record offset 16, `offsetPersistDirectory` = uint32 at record offset 20 (record offset 0 = 8-byte header)) back through the chain, merge `PersistDirectoryAtom` (0x1772; entries = uint32 with `persistId` = low 20 bits and `count` = high 12 bits, followed by `count` uint32 offsets; newest wins), then walk only the top-level records at those offsets. Within them collect atoms in `SlideListWithText` (0x0FF0) **instance 0** (placeholder text: slides; instance 1 = masters, 2 = notes) and inside Slide containers 0x03EE (free text boxes, table cells). Record header: uint16 `verInst` (ver = low 4 bits, instance = high 12), uint16 type, uint32 length; ver 0xF = container. TextCharsAtom = UTF-16LE, TextBytesAtom = Latin-1/CP1252 bytes; `\r` and `\v` (0x0B) separate paragraphs/lines.
* Differences vs POI in `live`: it includes table cell text POI skips (`testPPT_various`), and misses a few shape strings POI reports (`alterman_security` 0.899: some "Level 1.." strings; also includes a slide POI omits). Not expected to matter for resume material but not verified against a viewer.
* Encrypted PPT (`Password_Protected-*.ppt` exist in POI test-data) not tested; `UserEditAtom` has an `encryptSessionPersistIdRef` / the `CryptSession10Container` marks them. Report as unsupported.

## Risks to carry into M2

1. Expected text is not viewer-verified (see method). Add a few user-supplied HWP/DOC/PPT files to the M2 regression set when available.
2. Korean-language DOC/PPT untested (no public samples found).
3. Table-cell ordering in HWP is stream order (host paragraph then cells); layout order may differ for nested tables.
4. Distribution-document copy restrictions: decrypting is technically trivial (no secret is involved) but the product should decide whether to process them; HWPX distribution docs are not decryptable here.
5. Embedded OLE objects, images (OCR) and equations (`<수식>`) are out of scope; pyhwp-matrix shows equation-only documents yield empty text.
